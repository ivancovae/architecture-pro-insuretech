# Анализ проблем и рисков текущей архитектуры

## Проблемы производительности и масштабируемости

1. С повышением количества страховых компаний (до 10), существенно, увеличится время ответа сервиса ins-product-aggregator в синхронных вызовов.
2. Риск таймаутов, при медленных ответах, от страховых компаний, риски нарушения, заявленных, SLA.
3. Низкая отказоустойчивость - сбой одной компании влияет на весь агрегированный ответ.
4. Один партнер может исчерпать все ресурсы. Сервис ins-product-aggregator станет узким местом при масштабировании API для систем партнеров.
5. Общее время ответа определяется временем ответа самого медленного API страховой компании.

## Проблемы данных и консистентности

1. Локальные реплики данных могут расходиться между сервисами.
2. Core-app может привести к показу устаревших тарифов. Минутная (десятки минут) задержка и суточная задержки обновления продуктов в core-api может привести к неактуальности данных.
3. Нет механизма гарантированной доставки данных об оформленных страховках.
4. Каждый сервис использует свою схему в одной базе данных PostgreSQL, развернутой в единственном экземпляре. Это создает единую точку отказа и может стать узким местом при росте нагрузки.

## Операционные риски

1. Сложность мониторинга и отладки цепочки вызовов - увеличенное время разбора инцидентов.
2. Увеличение времени агрегации продуктов.
3. Риск потери данных при сбоях во время выгрузки реестров - до следующего обновления данные будут неактуальные.
4. Рестрикции, или защиты от перегрузки систем страховых компаний - каждый запрос приводит к множеству запросов ко всем страховым компаниям, что может создать значительную нагрузку на API страховых компаний и привести к ограничениям с их стороны.
